# 人事管理系统（employee-sys）

一个纯内存的控制台人事管理系统，用于把 Java 基础篇（day01–day08）的知识点串成一条完整链路。

代码在 `src/tang/`，共 7 个文件、约 1115 行，全部中文注释。

## 怎么运行

**IDEA**：打开 `employee-sys` 模块，右键 `EmployeeSystem.java` → Run `main`。
若中文显示乱码，在运行配置的 VM options 里加 `-Dstdout.encoding=UTF-8`。

**命令行**：

```bash
javac -encoding UTF-8 -d out src/tang/*.java
java -Dstdout.encoding=UTF-8 -cp out tang.EmployeeSystem
```

`-encoding UTF-8` 和 `-Dstdout.encoding=UTF-8` 都不能省——源码含中文，Windows 控制台默认代码页不是 UTF-8。

## 已知边界与练习

以下是**刻意保留**的问题。它们不影响正常使用，但都是真实存在的边界——留给你自己动手改，比看别人改学到的多。每条都给了触发条件、影响和修复思路。

### 练习 1：工号可以是空串

**触发**：菜单 1 添加员工时，在「请输入工号」处直接按回车。

**现象**：空工号的员工会被成功添加，此后可以查到、也能删除，只是工号那一列是空的。

**为什么没修**：设计文档已声明「数值、文本不做合法性校验」，而「空串算不算非法工号」属于业务规则，不同系统的答案不一样。

**修复思路**：`EmployeeSystem.java` 的 `addEmployee()` 里，读到工号后加一句判断：

```java
if (id.length() == 0) {
    System.out.println("工号不能为空，操作已取消。");
    return;
}
```

**进阶思考**：`EmployeeService.add()` 里的防御挡的是 `null`，为什么不挡空串？如果只在 service 层挡，和在界面层挡，有什么区别？（提示：service 是「唯一的数据容器」，它该不该对数据的合法性负责？）

---

### 练习 2：`findById()` 返回的是内部对象本身

**触发**：拿到 `findById()` 或 `findAll()` 的返回值后，修改元素对象的字段。

```java
Employee e = service.findById("E001");
e.setId(null);      // 这一改，就改到了容器里的真实数据
```

**现象**：容器被污染。此后 `findById` / `delete` / `update` 全部抛 `NullPointerException`，而 `add()` 里那两行入口防御**自己也会崩**——因为容器里那个元素的 id 是 null，`employees.get(i).getId().equals(...)` 直接崩。

**影响范围**：只有 `count()` 和几个统计方法还活着。整个服务基本不可用，而项目禁用 `try-catch`，调用方连自救手段都没有。

**为什么没修**：要真正隔离，得让 `findById()` 返回对象的副本（每次 new 一个），或者把 `Employee.setId()` 收起来。两者都会明显改变现有设计，超出这个项目的范围。

**这个练习的价值**：它说明了**入口防御只能守住「传进来的参数」，守不住「容器里已有的存量」**。想让不变量真的成立，得同时管住入口和出口。这是工程上很容易忽略的一点。

**修复思路**（任选）：
- 让 `findById()` 返回副本：需要给 `Employee` 加拷贝构造器
- 把 `setId()` 从 `public` 收紧（但 `Employee` 在 `tang` 包内，包内还是能调）
- 在 `findById()` 里做防御性检查，发现容器内数据异常时返回 `null`

### 练习 3：两处走不到的 `else` 分支

**位置**：`EmployeeSystem.java` 中 `addEmployee()` 的「添加失败：工号已存在。」与 `updateEmployee()` 的「修改失败。」

**为什么走不到**：这两处之前已经做了预检（添加前查重、修改前查存在性），单线程下预检通过了，后面的 `service.add()` / `service.update()` 就不可能失败。

**为什么没修**：这是「预检失败 → 兜底」的防御性写法，删掉反而降低健壮性——万一将来预检规则和 service 的规则分叉了，兜底就会生效。

**留给你思考**：这是「冗余」还是「防御」？如果给它加一句注释说明「正常情况下不会走到」，是不是比删掉更好？

### 已知限制（设计层面，不是缺陷）

这几条是设计时就明确接受的，不是遗漏：

1. **数据不持久化**：程序一关，添加的员工全部消失。做文件读写要先学 IO 章节。
2. **中文表格列宽对不齐**：`String.format("%-8s", name)` 按**字符个数**补空格，而一个汉字在终端占**两个字符宽**。要真正对齐得自己算显示宽度。
3. **输入非数字会中断程序**：`nextInt()` 遇到 `abc` 会抛 `InputMismatchException`，程序直接退出。要修它得先学异常处理——**你现在正在学（day09），学完可以回来把这个洞补上**，这是个很好的练手目标。
4. **数值不做合法性校验**：输入 `-5` 岁的员工会被接受。
